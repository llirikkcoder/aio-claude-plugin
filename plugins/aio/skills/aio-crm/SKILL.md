# AI Office CRM через MCP

Инструменты приходят как `mcp__plugin_aio_aio__<имя>`. Если AI Office уже
подключён вручную (`claude mcp add … ai-office`), Claude Code гасит сервер
плагина как дубль, и те же инструменты называются `mcp__ai-office__<имя>` —
правила ниже одинаковы для обоих.
Полный список с разделами доступа — [references/tools.md](references/tools.md).

## Компания и права задаёт ключ

- Ключ MCP привязан к **одной** компании. `company_id` почти всегда можно не
  передавать: сервер подставит компанию ключа. Если передать чужую — 403
  «This API key is limited to another company». Не перебирать номера.
- Какая компания у ключа — `get_context` → поле `company_id_from_header`.
- Права выдаются по разделам: `deals`, `contacts`, `tasks`, `projects`,
  `products`, `offers`, `campaigns`, `companies`, `people`, `audit`,
  `content-plan`; уровни `r`, `rw`, `rwd`. Отказ выглядит как
  «This API key has no access to '<раздел>'» — это не поломка, а граница ключа.
  Сказать пользователю, какой раздел нужно отметить в кабинете, и не пытаться
  обойти через другой инструмент.
- `read_file` / `list_files` / `propose_changes` есть в списке, но ключам
  компаний отвечают отказом: доступ к исходникам даётся только внутреннему ключу.

## Чтение: что свежее, а что снимок

- `list_tasks` и `list_epics` — чтобы найти кандидатов. Они могут отдавать
  **устаревший снимок** статусов и не несут комментариев.
- Перед тем как менять статус, назначать или делать вывод о задаче, перечитать её
  через `get_epic_with_subtasks(epic_id)`. Он принимает и UUID, и номер задачи
  (`"921"`), работает и для обычной задачи (тогда `children: []`) и возвращает
  комментарии. Иначе легко перетереть чужое свежее решение.
- Решение по сделке часто лежит в её заметках (`notes`), а не в статусе.
  Прежде чем говорить «сделка стоит/закрыта», прочитать `get_deal`.
  Заполненное поле (ссылка на договор и т.п.) — не факт подписания.

## Запись: осторожно, это живая CRM

- Все данные — боевые. Проверять пишущий вызов (особенно `update_deal_status`,
  `delete_*`) на заведомо безопасной записи, а не на первой из списка.
- Перед массовой правкой (больше 3 записей) показать пользователю список и
  дождаться согласия.
- `delete_campaign` удаляет насовсем; `delete_product` и `delete_offer` —
  архивируют.
- Статусы сделок делятся на стадии воронки (`new_request` … `won`, `done`) и
  закрытие без успеха (`rejected`, `cancelled`); `lost` нет. Статусы задач:
  `pending`, `in_progress`, `under_review`, `completed`, `blocked`,
  `cancelled`, `paid`. Сервер — источник правды: при сомнении смотреть
  `get_context` (`deal_statuses`, `deal_closing_statuses`, `task_statuses`).
- `assign_task`: исполнитель и проверяющий должны совпадать с участником из
  `list_people` (имя как там). Выдуманное имя — ошибка.
- `add_task_comment`: `user_id` — UUID участника из `list_people`, не имя.
- `create_task(..., project_id=…)` кладёт задачу в проект,
  `parent_task_id` делает её подзадачей эпика.
- Неизвестное поле при записи возвращает ошибку — не угадывать имена полей,
  смотреть описание инструмента.

## Когда нужен человек

`flag_for_human(message, context?, urgency?)` шлёт владельцу компании сообщение
в Telegram и заводит задачу с высоким приоритетом. Для решений, которые агент
принимать не вправе: деньги, сроки, скидки, юридическое, непонятное состояние
данных. Не использовать для отчётов о ходе работы.

## Ответ пользователю

- Цифры и статусы — только из ответа инструмента в этой же беседе. Не
  дополнять по памяти.
- Ссылки на задачи сервер кладёт в ответ сам (`url`) — давать их, а не номера
  без ссылок.
- Ошибка подключения (401/404/нет инструментов) → команда `/aio:check`.
